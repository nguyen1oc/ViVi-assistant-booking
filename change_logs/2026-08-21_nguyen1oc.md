# Changelog — 2026-08-21 (nguyenloc)

## Phạm vi thay đổi
Fix toàn bộ luồng giữ chỗ / hủy chỗ lái thử: slot không được giải phóng khi bấm "Hủy" hoặc chọn slot mới, dẫn đến slot kẹt trạng thái `held` mãi mãi và người dùng không thể đặt lại.

---

## Root Cause

```
User bấm "Hủy"
  → Frontend gọi releaseBookingHold()
  → POST /api/v1/chat  ← SAI ENDPOINT → 422 Unprocessable Entity
  → Guardrails chặn ngay cả khi đúng endpoint → 400 Bad Request
  → Slot KHÔNG được release trong DB/Redis
  → User bấm chọn lại slot cũ
  → Backend thấy slot vẫn "held" → trả lỗi "không còn khả dụng"
  → Frontend xóa slot khỏi lịch (setSlots([]))
  → Vòng lặp lỗi
```

---

## Các File Đã Thay Đổi

### Backend

#### `backend/src/guardrails/policies.py`
- Thêm `"release_hold": frozenset({"booking_id"})` vào `DEMO_ACTION_ALLOWED_FIELDS`
- **Lý do**: Guardrails block 100% mọi request `release_hold` vì action này không có trong allowlist → trả 400 trước khi tới handler

#### `backend/src/services/booking/lifecycle.py`
- Import `redis_client` (đã làm session trước)
- Sửa SQL trong `release_hold`: `WHERE current_booking_id=?` → `WHERE id=? OR current_booking_id=?`
- Gọi `redis_client.delete_slot_hold(slot_id)` sau khi release DB
- **Lý do**: Câu SQL cũ có thể không match được dòng slot nếu `current_booking_id` chưa được ghi đúng → slot kẹt `held` trong DB và Redis

#### `backend/src/config.py`
- Tăng `rate_limit_chat_per_session_per_minute` default: `10` → `30`
- **Lý do**: Khi test nhanh (chọn slot → hủy → chọn lại), frontend gửi 3–4 request `/chat` liên tiếp trong vài giây, vượt ngưỡng 10 req/min

### Frontend

#### `frontend/src/api/booking.js`
- Thêm export `releaseBookingHold(bookingId)`
- Đổi từ `agentAction` (POST `/api/v1/chat`) sang `bookingManagementAction` (POST `/api/v1/test-drive/actions`)
- **Lý do**: `/chat` endpoint không biết xử lý action `release_hold` → 422; phải dùng `/test-drive/actions` giống các action quản lý booking khác

#### `frontend/src/pages/BookingPage.jsx`

**1. Release slot cũ khi chọn slot mới (trong `confirmSlot`)**
- Nếu đang giữ `bookingId` cho slot `A` mà user bấm chọn slot `B` → tự động `releaseBookingHold(bookingId)` + khôi phục màu xanh slot `A` + `holdActionIdsRef.current.clear()` trước khi hold slot `B`

**2. Release slot đúng cách khi bấm "Hủy" (trong `onBack` của `CustomerForm`)**
- Gọi `releaseBookingHold(currentBookingId)`
- Cập nhật slot cũ về `isAvailable: true` ngay trên local state (không refetch)
- Clear `holdActionIdsRef.current` để tránh tái sử dụng `ui_action_id` cũ
- Không gọi `searchBookingOptions` (tránh làm mất lịch)

**3. Không xóa lịch khi gặp lỗi hold (trong `catch` của `confirmSlot`)**
- Bỏ `setSlots([])` trong nhánh catch
- Bỏ `setSlots(groupSlots(refreshed.slots))` khi gặp `SLOT_NO_LONGER_AVAILABLE`
- Thay bằng: chỉ `setPendingSlot(null)` + `setSelectedSlot(null)`, giữ nguyên toàn bộ lịch trên UI

**4. Tạo `ui_action_id` mới mỗi lần hold**
- Bỏ cơ chế cache `holdActionIdsRef.current.get(actionKey)` → dùng `actionId('hold')` trực tiếp
- **Lý do**: `ui_action_id` cũ bị cache lại → backend trả idempotent response của lần hold đã bị cancel → báo lỗi "không còn khả dụng"

## Lưu ý Deploy
- Cần **rebuild cả backend lẫn frontend** để các thay đổi có hiệu lực trong Docker
- Thêm vào `.env` để tăng rate limit mà không cần rebuild backend:
  ```
  RATE_LIMIT_CHAT_PER_SESSION_PER_MINUTE=60
  RATE_LIMIT_CHAT_PER_SESSION_PER_HOUR=600
  ```

```bash
docker compose build backend frontend && docker compose up -d backend frontend
```
